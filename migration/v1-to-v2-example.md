# Example Migration: v1.0 → v2.0 (Hypothetical)

> HYPOTHETICAL: no v2.0 of the harness exists. The v1/v2 API surfaces below are invented for illustration. The detector output is generated by `scripts/generate_migration_example.py` (run with `python -m scripts.generate_migration_example`), not typed.

This example shows what a v2.0 migration guide would look like if `HarnessConfig`
were renamed to `HarnessSettings` and `with_retry` gained a required `policy` param.

## Breaking Changes in v2.0

| Change | Affected Callers | Migration Step |
|---|---|---|
| `HarnessConfig` renamed to `HarnessSettings` | `from harness_core import HarnessConfig` | Replace with `HarnessSettings` |
| `with_retry` gains a required `policy` parameter | `await with_retry(fn, ...)` | Pass `policy` explicitly |

## Detection

The fixed detector (`versioning/breaking_change_detector.py`) run on the hypothetical v1 and v2 sources in the generator script reports:

<!-- DETECTOR-OUTPUT:START -->
```
removed_name: 'HarnessConfig' removed from public API
required_param_added: Required parameters added to 'with_retry': ['policy']
```
<!-- DETECTOR-OUTPUT:END -->

If a CI gate ran the detector and the compatibility suite, it could fail on both changes before release. That is a hypothetical: this repo has no CI workflow and no timing was measured.

## Fix

```python
# Before (v1)
from harness_core import HarnessConfig
config = HarnessConfig(max_retry_attempts=3)

# After (v2)
from harness_core import HarnessSettings
config = HarnessSettings(max_retry_attempts=3)
```
